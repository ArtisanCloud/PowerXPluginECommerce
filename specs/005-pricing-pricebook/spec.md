## User Scenarios & Testing *(mandatory)*

### User Story 1 - 创建并发布价目表版本 (Priority: P1)

定价经理可以创建价目表，并通过“版本”管理价格变更：在草稿版本中维护价格条目，提交发布后在指定生效时间起对外生效；可在必要时下线版本，避免错误价格扩散。

**Why this priority**: 价目表是定价中心的主数据地基；没有“版本发布”就无法安全地把价格变更投放到订单/前台/渠道。

**Independent Test**: 仅实现“新建价目表→新建草稿版本→发布→生效→下线/回滚到安全状态”的流程，即可形成可演示、可验收的最小闭环。

**Acceptance Scenarios**:

1. **Given** 租户内尚无目标价目表，**When** 定价经理创建价目表并生成一个草稿版本，**Then** 系统应能展示该价目表主档与草稿版本，且草稿版本可继续编辑。
2. **Given** 价目表存在草稿版本，**When** 定价经理发布该版本并设置“立即生效”或“定时生效”，**Then** 在生效时间点后对外查价应使用该版本作为基础价来源。
3. **Given** 某价目表已存在一个已生效版本，**When** 定价经理发布一个新版本，**Then** 系统应确保在任一时刻对外生效的版本满足“一致、可解释”的规则（不会出现同一价目表多个版本同时生效导致的不确定性）。
4. **Given** 已生效版本出现配置错误风险，**When** 定价经理下线该版本，**Then** 对外查价不应再命中该版本，并应回到安全的兜底结果（例如基础价目表或明确的“无价”响应，具体以本规格的回退策略为准）。

---

### User Story 2 - 维护价目表适用范围与价格条目 (Priority: P2)

定价经理可以为价目表绑定适用范围（例如渠道、客户组、供应商等维度），并维护每个 SKU 的基础价/销售价/建议零售价/成本价/最低最高价等条目；支持批量覆盖部分 SKU，避免全量重复维护。

**Why this priority**: 价目表的业务价值来自“同一商品在不同对象/渠道下呈现不同基础价”；没有“范围 + 条目”就无法支撑差异化定价。

**Independent Test**: 仅实现“选择范围→维护若干 SKU 的价格条目→对外查价能命中范围与条目”的链路即可独立验收。

**Acceptance Scenarios**:

1. **Given** 价目表未配置任何适用范围限制，**When** 对外按不同渠道/客户组发起查价，**Then** 该价目表应被视为“全量适用”（不因缺少范围而无法命中）。
2. **Given** 价目表配置了某维度的适用范围，**When** 查价上下文不包含该维度或不在范围内，**Then** 系统不应命中该价目表（避免误用错误价）。
3. **Given** 草稿版本存在若干 SKU 价格条目，**When** 定价经理编辑条目并保存，**Then** 发布前对外查价不应受到草稿改动影响；发布后才生效。
4. **Given** 同一 SKU 在条目中同时存在多类价格字段，**When** 对外查价需要输出“基础成交价”，**Then** 系统应按约定的字段优先级产生可解释的最终基础价（并能说明来源字段）。

### User Story 3 - 统一的基础查价能力供多系统复用 (Priority: P3)

订单系统、前台/小程序、渠道同步等消费者可以通过统一的“查价”能力，在给定上下文（SKU、币种、渠道/客户/供应商、时间点等）时得到可用于后续计算的“基础价格结果”，并包含必要的可追溯信息（命中哪个价目表/版本、回退原因等）。

**Why this priority**: 统一查价是跨模块一致性的关键；否则每个系统都会各自解释价格来源，导致对账与售后争议。

**Independent Test**: 仅实现“输入上下文→返回基础价 + 命中来源 + 回退信息”的响应即可独立演示，并可被多个调用方复用。

**Acceptance Scenarios**:

1. **Given** 存在满足上下文的生效价目表版本与对应 SKU 条目，**When** 发起查价，**Then** 系统应返回基础价与命中来源信息（价目表、版本、生效时间）。
2. **Given** 范围匹配命中了某价目表版本，但该版本不存在该 SKU 条目，**When** 发起查价，**Then** 系统应按统一回退策略返回结果，并在回退信息中标明“为何回退”。
3. **Given** 在同一时间点存在多个候选价目表可命中，**When** 发起查价，**Then** 系统应按“更具体优先/优先级规则（如存在）/最近发布”等确定性规则选择一个结果，且可解释。
4. **Given** 因配置/数据缺失导致无法定价（例如范围不命中或无任何可用版本），**When** 发起查价，**Then** 系统应返回“无价”结果并携带可枚举原因码，供调用方决定展示或拦截策略。
5. **Given** 请求参数缺失或非法（例如缺少 SKU 或币种格式非法），**When** 发起查价，**Then** 系统应返回“错误”响应并携带错误码，供调用方修正请求。
6. **Given** 同一价目表已有生效版本，**When** 发布一个新版本并设置生效时间，**Then** 系统应自动终止旧版本在该时间点后的有效性，避免出现同一时刻多个版本同时可命中。

### Edge Cases

- 当生效时间与失效时间配置不合法（例如失效早于生效）时如何处理（保存/发布时阻止并给出明确提示）。
- 当币种不一致（请求币种与价目表币种不一致）时如何处理（不命中并返回无价/错误；不回退到 Base 以避免误用错误币种）。
- 当上下文缺失范围维度（例如未提供渠道）但价目表限制了该维度时如何处理（不命中并返回无价/错误；不回退到 Base 以避免绕过范围约束）。
- 当同一 SKU 在多个范围重叠的价目表中同时可命中时的选择与解释策略（必须确定性、可追溯）。
- 当查价在“切换版本生效”的时间边界附近发生时如何保证一致性（不出现短时间内随机命中不同版本的现象）。

## Requirements *(mandatory)*

### Assumptions

- 价目表、版本、条目与适用范围均为“租户隔离”的业务数据。
- 一期只覆盖“基础价目表（静态基础价）”能力；阶梯价/客户价/合同价/促销/优惠券/礼品卡等属于后续叠加层，查价返回结构需可扩展但不要求一期计算。
- 一期支持多币种，但不包含自动汇率换算；调用方需按目标币种选择对应价目表或明确无价。

### Functional Requirements

- **FR-001**: 系统 MUST 支持创建、查看、更新、归档价目表主档，并支持按关键字段检索与筛选（如名称、类型、币种、状态）。
- **FR-002**: 系统 MUST 支持价目表的版本化管理，至少包含草稿与已生效两类状态，并能记录版本的生效与失效时间。
- **FR-003**: 系统 MUST 支持在草稿版本中维护价格条目（按 SKU 维度），并在发布前保证对外查价不受草稿影响。
- **FR-004**: 系统 MUST 支持发布版本并按生效时间使其对外可用；发布后应保证同一价目表在任一时刻的生效版本选择是确定性的。
- **FR-004A**: 系统 MUST 在发布新版本时自动处理旧版本：将旧版本有效期终止为“新版生效时间点”（或等效下线），以保证同一价目表在任一时刻最多只有一个版本可被命中。
- **FR-005**: 系统 MUST 支持下线已生效版本，并使其不再对外可被命中；下线行为必须可追溯。
- **FR-006**: 系统 MUST 支持为价目表配置适用范围（至少覆盖渠道、客户组、供应商维度），并在查价时正确判断“范围限制”与“全量适用”。
- **FR-007**: 系统 MUST 定义并执行价格字段的优先级规则，以输出“基础成交价”；同时返回必要的来源解释信息（来自哪个字段/价目表/版本）。
- **FR-007A**: 系统 MUST 固化“基础成交价”的字段优先级顺序为：`sale_price`（销售价）> `base_price`（基准价）> `msrp`（建议零售价）；并在查价结果中返回 `source_field`（指明最终价格来自哪个字段）。
- **FR-008**: 系统 MUST 提供统一的查价能力：输入 SKU、币种、时间点与可选上下文维度，输出基础价结果与命中来源、回退信息。
- **FR-009**: 系统 MUST 定义一致的回退策略，并确保所有调用方得到一致行为：仅当“已命中某价目表的生效版本，但该版本缺少目标 SKU 条目”时，才允许回退到同币种的 `Base Pricebook`；当“范围不命中、币种不匹配、无任何候选价目表版本可用”等情况发生时，应直接返回无价/错误而不回退。
- **FR-010**: 系统 MUST 记录关键操作的审计信息（至少包含价目表/版本的创建、更新、发布、下线，以及条目批量变更的摘要），以便追溯与排查。
- **FR-011**: 系统 MUST 在并发编辑与发布场景下保证数据一致性（避免重复发布、错乱生效期、版本指针不一致），并对冲突返回可定位的错误。
- **FR-012**: 系统 MUST 在存在多个候选价目表可命中时，按确定性选择规则返回唯一结果，并可解释：优先选择“更具体”的价目表（范围限制维度更多/更精确），若仍冲突则按价目表显式优先级（如配置）选择，若仍相同则选择最近发布版本的结果。
- **FR-013**: 系统 MUST 统一查价失败语义：当因“配置/数据缺失（例如无可用价目表版本、范围不命中、条目缺失且不满足回退条件等）”导致无法定价时，应返回“无价”结果并携带可枚举的原因码；当因“请求参数缺失/非法、币种非法”等导致无法处理请求时，应返回明确错误并携带错误码。

### Key Entities *(include if feature involves data)*

- **价目表 (Pricebook)**: 表示一组基础价格策略的主档，包含币种、类型、状态与适用范围定义。
- **价目表版本 (Pricebook Version)**: 表示价目表在某个时间段内生效的不可变快照（或可发布快照），用于安全投放价格变更。
- **适用范围 (Scope)**: 表示价目表适用的对象集合（如渠道/客户组/供应商），用于决定是否可命中。
- **价格条目 (Pricebook Item)**: 表示某版本下某个 SKU 的各类价格字段集合（基础价/销售价/MSRP/成本/最低最高价等）。
- **查价上下文 (Pricing Context)**: 查价输入所携带的 SKU、币种、时间点与维度信息集合。
- **基础查价结果 (Price Quote)**: 查价输出的基础成交价及其来源解释、回退信息，用于被订单/促销等后续层消费。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 定价经理可以在 ≤ 5 分钟内完成“创建价目表 + 创建草稿版本 + 录入 10 个 SKU 条目 + 发布并立即生效”的完整流程，并在生效后查价可验证命中来源。
- **SC-002**: 对外查价能力在正常负载下响应时间满足 P95 ≤ 200ms，且结果选择规则确定性可复现（相同上下文在同一时间点返回一致结果）。
- **SC-003**: 发布/下线操作具备可追溯性：任一次价格变更都能在 ≤ 1 分钟内定位到对应的价目表、版本与操作者信息（通过审计记录）。
- **SC-004**: 在“范围不命中/条目缺失/币种不匹配”等场景下，系统返回的失败或回退结果可解释且一致，相关售后/运营问题定位时间降低（以团队内部复盘为准）。
