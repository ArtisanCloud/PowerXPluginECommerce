# Feature Specification: 促销规则引擎（订单自动促销）

**Feature Branch**: `015-pricing-promotions-engine`  
**Created**: 2026-06-10  
**Status**: Draft

## Clarifications

### Session 2026-06-10

- Q: 多条促销命中且属于同一互斥组时，应该如何选择最终应用的促销？ → A: 互斥组内选择优惠金额最大的促销。
- Q: 促销与优惠券都可用时，如果促销配置为不允许与优惠券叠加，最终结算应该怎么处理？ → A: 保留促销，拒绝优惠券，并返回 `promotion_excludes_coupon` 原因。
- Q: 促销有效期结束边界应该如何判定？ → A: 含结束边界，订单提交时间小于等于结束时间时促销可用。
- Q: 一期促销优惠金额分摊到订单行时，应该采用什么口径？ → A: 按订单行促销前金额占比分摊。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 配置并启用基础促销规则 (Priority: P1)

作为定价经理或营销运营人员，我需要在定价中心创建订单级满减或折扣促销，并设置有效期、适用范围、渠道和叠加规则，使促销能够在订单结算中自动生效。

**Why this priority**: 没有可管理的促销规则，订单侧无法稳定复用促销配置；这是促销引擎的最小可交付能力。

**Independent Test**: 创建一条订单满减促销，启用后在促销列表中按状态、类型和关键词能查询到，并能查看其范围、门槛、优惠动作和叠加配置。

**Acceptance Scenarios**:

1. **Given** 运营填写了促销编码、名称、类型、有效期、门槛和优惠动作，**When** 保存为草稿，**Then** 系统创建促销规则且状态为 draft。
2. **Given** 一条促销规则处于 draft 或 paused，且有效期配置合法，**When** 运营启用促销，**Then** 系统将其标记为 active 并记录操作人和操作时间。
3. **Given** 一条促销规则处于 active，**When** 运营停用促销，**Then** 系统将其标记为 paused，并且后续订单结算不再命中该促销。
4. **Given** 运营复制一条已有促销，**When** 复制完成，**Then** 系统生成一条新的草稿促销，并保留原促销的规则配置供编辑。

---

### User Story 2 - 订单结算自动命中促销 (Priority: P2)

作为下单用户或代客下单人员，我需要系统在结算时自动应用符合条件的促销，并返回可解释的优惠明细，避免人工选择或前后端金额不一致。

**Why this priority**: 自动促销必须进入订单金额计算，才能产生真实交易价值；该能力让促销规则从运营配置变成交易闭环。

**Independent Test**: 准备满足门槛的订单草稿和一条 active 满减促销，执行结算试算后应返回促销前金额、促销优惠、促销后金额和命中的促销明细。

**Acceptance Scenarios**:

1. **Given** 订单满足 active 促销的有效期、渠道、SKU 范围和金额门槛，**When** 用户进入结算或提交订单，**Then** 系统自动应用促销并展示促销优惠金额。
2. **Given** 订单不满足促销门槛或适用范围，**When** 系统执行结算，**Then** 该促销不会影响应付金额，并返回可枚举的未命中原因。
3. **Given** 多条促销同时符合条件，**When** 系统执行结算，**Then** 系统按优先级、互斥组和叠加规则决定最终应用的促销集合。
4. **Given** 促销与优惠券都可用于同一订单，**When** 系统执行结算，**Then** 系统先计算促销，再按促销的券叠加规则决定是否继续应用优惠券。
5. **Given** 小程序用户进入确认订单页，**When** 页面加载订单草稿，**Then** 页面必须调用促销试算并展示自动促销优惠、已享活动和促销后合计。
6. **Given** 小程序确认订单页试算失败，**When** 用户继续提交订单，**Then** 提交流程不得信任前端试算金额，后端必须重新计算促销并返回最终订单金额。

---

### User Story 3 - 订单促销快照与客服追踪 (Priority: P3)

作为客服、财务或运营人员，我需要查看订单当时命中的促销与未命中原因，确保售后、对账和活动复盘时能够解释订单金额。

**Why this priority**: 促销配置会随时间变化，订单必须保存当时的促销计算结果，否则后续无法解释历史订单金额和优惠成本。

**Independent Test**: 创建并支付一笔命中促销的订单后，按订单号查询订单详情，应能看到促销优惠汇总、命中促销、未命中原因和分摊信息。

**Acceptance Scenarios**:

1. **Given** 订单在创建时命中一条或多条促销，**When** 订单保存成功，**Then** 系统保存该订单的促销计算快照。
2. **Given** 后续运营修改或停用促销规则，**When** 客服查看历史订单，**Then** 历史订单展示的促销金额和促销明细保持不变。
3. **Given** 订单发生售后或对账争议，**When** 客服按订单号查询，**Then** 系统能展示促销优惠总额、命中促销、未命中促销原因和订单行分摊结果。
4. **Given** 小程序用户打开订单详情页，**When** 订单存在促销快照，**Then** 页面必须展示自动促销优惠金额和订单创建时已享活动名称。

---

### Edge Cases

- 促销有效期边界：订单提交时间等于促销结束时间时，系统必须视为可用；提交时间晚于结束时间时才不可用。
- 促销配置无效：折扣比例、满减金额、有效期或范围配置不合法时，系统必须阻止启用或返回明确错误。
- 多促销冲突：多条促销属于同一互斥组时，系统必须只应用优惠金额最大的一条促销。
- 不可叠加促销：命中不可叠加促销后，系统必须阻止后续同层促销继续叠加。
- 促销排斥优惠券：促销配置不允许与优惠券叠加时，订单必须保留促销、拒绝优惠券，并展示 `promotion_excludes_coupon` 拒绝原因。
- 订单无促销：没有任何促销命中时，订单金额必须与基础定价和优惠券既有逻辑保持一致。
- 历史一致性：促销规则后续被编辑、停用或删除后，历史订单快照不得被重新计算覆盖。
- 租户隔离：不同租户的促销规则、命中记录和订单快照必须互不可见。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须允许授权用户创建订单级促销规则，至少支持满减和折扣两种促销类型。
- **FR-002**: 系统必须允许授权用户配置促销的编码、名称、说明、有效期、状态、适用渠道、适用范围、金额门槛、优惠动作和叠加规则。
- **FR-003**: 系统必须保证同一租户内促销编码唯一，并在编码冲突时阻止保存。
- **FR-004**: 系统必须支持促销规则的草稿、启用、停用和过期状态，并只允许 active 且在有效期内的促销参与订单结算；有效期结束时间含边界。
- **FR-005**: 系统必须在启用促销前校验核心规则完整性，包括有效期、促销类型、优惠动作、适用范围和叠加规则。
- **FR-006**: 系统必须允许运营按关键词、类型、状态、渠道和有效期筛选促销规则。
- **FR-007**: 系统必须允许运营复制已有促销规则，并将复制结果保存为新的草稿规则。
- **FR-008**: 系统必须在订单结算时自动匹配符合条件的促销规则，无需用户手动选择促销。
- **FR-009**: 系统必须支持全场促销、指定 SKU 促销和指定渠道促销的匹配判断。
- **FR-010**: 系统必须支持订单金额门槛判断，并在门槛不满足时提供明确拒绝原因。
- **FR-011**: 系统必须按促销优先级、互斥组和可叠加配置决定多条促销的应用结果；同一互斥组内必须选择优惠金额最大的促销。
- **FR-012**: 系统必须先计算促销优惠，再计算优惠券；当促销不允许与优惠券叠加时，系统必须保留促销、拒绝优惠券，并返回 `promotion_excludes_coupon` 原因。
- **FR-013**: 系统必须返回促销前金额、促销优惠金额、促销后金额、命中促销列表和未命中原因。
- **FR-014**: 系统必须将促销优惠金额按订单行促销前金额占比分摊到订单行，以支持售后和对账解释。
- **FR-015**: 系统必须在订单创建成功时保存促销快照，且后续促销配置变更不得改变历史订单快照。
- **FR-016**: 系统必须记录促销创建、修改、启用、停用、复制和订单命中的审计信息。
- **FR-017**: 系统必须保证未命中促销的订单不改变既有价格、优惠券、支付和售后流程。
- **FR-018**: 系统必须按租户隔离促销规则、促销快照和审计记录。
- **FR-019**: 系统必须向用户展示友好的规则校验错误，避免运营保存无法参与结算的促销。
- **FR-020**: 系统一期不得要求完整营销活动、预算审批、素材投放或渠道同步能力才能使用基础促销规则。
- **FR-021**: 小程序确认订单页必须展示自动促销试算结果，包括促销优惠、已享活动和促销后合计；试算失败时必须降级提示且不阻塞后端提交复算。
- **FR-022**: 小程序下单服务必须在创建订单时重新执行服务端促销计算，并以服务端结果更新订单总额和促销快照。
- **FR-023**: 小程序订单详情页必须从订单促销快照展示历史促销结果，不得根据当前促销规则重新计算历史订单。

### Key Entities *(include if feature involves data)*

- **促销规则 (Promotion Rule)**: 运营配置的优惠规则，包含类型、有效期、状态、适用范围、条件、动作和叠加策略。
- **促销条件 (Promotion Condition)**: 判断订单是否符合促销的条件集合，例如金额门槛、渠道、SKU 范围和时间窗口。
- **促销动作 (Promotion Action)**: 促销命中后产生的优惠方式，例如固定金额减免或比例折扣。
- **促销叠加策略 (Promotion Stacking Policy)**: 控制促销之间、促销与优惠券之间是否可叠加，以及优先级和互斥组。
- **促销结算结果 (Promotion Quote Result)**: 订单结算时输出的促销前金额、优惠金额、促销后金额、命中促销和未命中原因。
- **订单促销快照 (Order Promotion Snapshot)**: 订单创建时保存的促销计算结果，用于售后、客服解释和财务对账。
- **促销审计记录 (Promotion Audit Log)**: 记录促销配置变更、状态变更和订单命中情况的追踪数据。

### Assumptions

- 基础价格能力已存在，促销只在基础价结果上计算优惠，不改写基础价格。
- 优惠券能力已存在，促销与优惠券共享叠加和互斥语义。
- 一期促销范围以订单级满减和折扣为主，买赠、组合包、免邮、预算和渠道同步后续迭代。
- 一期用户侧落点为小程序确认订单、提交订单和订单详情；商品详情、购物车促销提示属于同一 feature 的增强项，但不阻塞 MVP。
- 金额计算以订单提交时的服务端结果为准，展示层可以预估但不能作为最终金额。
- 订单促销优惠按订单行促销前金额占比分摊。
- 促销有效性按订单提交时刻判定，时间精度到秒；提交时间小于等于促销结束时间时视为有效。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运营人员能在 5 分钟内完成一条订单级满减或折扣促销的创建、启用和列表查询。
- **SC-002**: 95% 的订单结算请求能在 500ms 内返回包含促销明细的最终金额结果。
- **SC-003**: 满足条件的促销在订单结算中的自动命中准确率达到 99.9%。
- **SC-004**: 不满足条件的促销在订单结算中不会影响应付金额，且 100% 返回可解释的未命中原因。
- **SC-005**: 命中促销的订单 100% 保存促销快照，且历史订单在促销变更后仍能展示原始促销金额。
- **SC-006**: 促销与优惠券叠加/互斥规则在验收样本中的计算结果 100% 符合配置预期。
- **SC-007**: 客服按订单号定位促销优惠来源的平均时间不超过 1 分钟。
- **SC-008**: 不使用促销的订单链路回归通过率达到 100%，订单金额无新增偏差。
