# Feature Specification: 自营下单 Checkout MVP

**Feature Branch**: `[007-order-mini-app]`  
**Created**: 2026-01-12  
**Status**: Draft  
**Input**: User description: "docs/plan/marketing/order/checkout_mvp.md"

目标是在 `one_time（一次性商品）` 范围内交付最小可用的下单闭环：统一可售校验 → 创建订单 → 锁库存 → 后台可查询/管理。订阅、真实支付、复杂履约、优惠叠加、售后/退款、第三方渠道订单同步不在本 MVP 范围内。

## Clarifications

### Session 2026-01-12

- Q: MVP 是否要为“创建订单（小程序/后台）”提供幂等机制来防止重试/重复点击导致的重复订单与重复库存锁定？ → A: 是。对小程序与后台的创建订单都支持幂等键；同一个幂等键重复提交返回同一订单结果。
- Q: MVP 中，哪些角色可以取消订单？哪些订单状态允许取消？ → A: 仅后台（运营/客服）可取消；仅 `pending_payment` 可取消（`paid` 不可取消，`draft` 可直接作废/删除不算取消）。
- Q: MVP 下单创建时，订单单价/金额以哪个时点的价格为准？如果价格在提交时与展示时不一致，要不要拒绝并要求用户确认？ → A: 以提交时服务端计算的当前价为准，直接创建订单并保存价格/金额快照；展示价仅供参考。
- Q: 当一次下单包含多个 SKU 时，如果其中任意一项不可售或库存不足，MVP 要如何处理？ → A: 整单原子：任一项失败则整单失败，不创建订单、不锁任何库存。
- Q: MVP 是否需要生成“人可读订单号”（不同于内部ID）？如果需要，唯一性范围是什么？ → A: 需要。生成人可读订单号，并要求在同一租户内唯一。
- Q: MVP 是否要做“收货地址”与“地址簿”？订单里地址如何保存？ → A: 要做。提供客户地址簿（可多条、可设默认），下单时选择地址并在订单中保存**地址快照**（订单历史不可被客户后续改地址影响）；同时订单可选保留 `shipping_address_id` 便于追溯来源地址记录。

## User Scenarios & Testing *(mandatory)*

### User Story 0 - 小程序购物车（混合模式：本地 + 服务端同步）(Priority: P1)

客户在小程序将 SKU 加入购物车并调整数量；购物车默认保存在本地（离线可用），登录后会与服务端购物车进行同步与合并，以支持多端一致的购物车体验；结算时将购物车 items 作为下单输入来源之一。

**Why this priority**: “加入购物车 → 结算下单”是最常见的购买路径之一；混合模式可在不增加过多后端复杂度的前提下提供多端体验，并为后续引入促销/预占等能力保留扩展点。

**Independent Test**:
1) 小程序加入购物车（本地可见）；2) 登录后调用 cart sync，服务端返回合并结果；3) 多端分别加购同一 SKU 后同步，数量按策略合并；4) 从购物车发起下单成功后，库存锁定仅在下单时发生。

**Acceptance Scenarios**:

1. **Given** 客户未登录（或离线），**When** 客户加入购物车并调整数量，**Then** 购物车在本地保存并可被再次打开查看，且不依赖服务端可用性。
2. **Given** 客户已登录且服务端存在历史购物车，**When** 客户触发购物车同步，**Then** 系统按约定合并策略返回统一购物车结果（默认 `max` 合并），且后续打开购物车展示一致。
3. **Given** 客户在两个设备分别加购同一 SKU，**When** 两端分别执行同步，**Then** 购物车在服务端与两端最终一致，且不会因重复同步造成数量翻倍（默认策略）。
4. **Given** 购物车中存在不可售/库存不足的 SKU，**When** 客户在结算时发起下单，**Then** 下单接口按统一口径拒绝并返回原因，且库存锁定不发生。

---

### User Story 1 - 小程序下单（一次性商品）(Priority: P1)

客户在小程序对可售（sellable=true）的 SKU 发起下单，系统在提交时进行服务端二次可售校验与库存校验，通过后创建订单并锁定库存；客户可查看订单列表与订单详情。

**Why this priority**: 这是“自营下单闭环”的核心价值交付，决定是否形成可用的最小闭环。

**Independent Test**: 在测试环境准备一个可售且库存充足的 SKU，使用小程序下单并验证订单创建成功、库存被锁、且订单可被该客户查询到；同时验证不可售/库存不足的下单会被拒绝且不会产生库存锁定。

**Acceptance Scenarios**:

1. **Given** 某 SKU 在指定渠道下满足可售门槛且可用库存充足，**When** 客户提交包含该 SKU 与数量的下单请求，**Then** 系统创建订单与明细并返回订单标识、状态与金额汇总，且对应库存被锁定。
2. **Given** 某 SKU 在提交时不满足可售门槛（例如已下架/不可售），**When** 客户提交下单请求，**Then** 系统拒绝创建订单并返回明确原因，且库存锁定不发生。
3. **Given** 某 SKU 可售但可用库存不足，**When** 客户提交下单请求，**Then** 系统拒绝创建订单并返回库存不足原因，且库存锁定不发生。
4. **Given** 客户已成功创建订单，**When** 客户查询订单列表或订单详情，**Then** 系统仅返回该客户可见的订单信息与明细，且订单状态与金额信息一致。

---

### User Story 2 - Web-admin 代客下单（运营/客服）(Priority: P2)

运营/客服在后台选择客户并为其创建订单（同样复用可售校验、价格快照、库存锁定口径），以便支持代客下单与业务补单等场景。

**Why this priority**: 代客下单是运营侧最常见的订单创建入口之一，能显著提升运营效率，并复用 P1 的核心能力。

**Independent Test**: 在后台选择某客户并创建包含可售 SKU 的订单，验证订单成功创建、库存锁定成功，并且该订单可被后台与该客户查询。

**Acceptance Scenarios**:

1. **Given** 运营/客服拥有创建订单权限且目标客户存在，**When** 运营/客服为该客户提交下单（SKU+数量+渠道），**Then** 系统创建订单并锁定库存，且订单关联到目标客户。
2. **Given** 目标 SKU 不可售或库存不足，**When** 运营/客服提交代客下单，**Then** 系统拒绝创建订单并返回原因，且库存锁定不发生。

---

### User Story 3 - 后台订单管理（列表/详情/取消/日志）(Priority: P3)

运营在后台查看订单列表与详情；可以取消尚未完成履约的订单；系统记录关键操作日志以便追溯。

**Why this priority**: 没有后台可查询与可取消能力，将无法形成可运营的闭环与风险控制；日志是问题定位与合规审计的基础。

**Independent Test**: 创建一笔订单后在后台检索到该订单并查看详情；执行取消操作并验证状态变化与库存解锁，同时能在操作日志中看到对应记录。

**Acceptance Scenarios**:

1. **Given** 系统中存在订单，**When** 运营在后台按条件查询订单列表，**Then** 系统返回匹配条件的订单列表并支持进入详情查看明细与金额信息。
2. **Given** 订单处于可取消状态，**When** 运营发起取消订单操作，**Then** 订单状态变为已取消，且对应库存锁定被释放。
3. **Given** 发生订单创建与取消等关键操作，**When** 运营查看订单操作日志，**Then** 系统展示时间、操作者、事件类型与关键字段，支持追溯。

### Edge Cases

- 并发下单导致同一 SKU 竞争库存时，系统如何保证“不会超卖”且不会留下部分锁定？
- 客户/运营重复提交相同下单请求时（例如网络重试），系统应通过幂等键避免产生重复订单或重复库存锁定（同一幂等键重复提交返回同一订单结果）。
- 取消订单时库存解锁的下限如何处理（例如避免解锁后出现负数或异常回滚）？
- 价格在“展示到提交”之间发生变化时，订单金额与价格来源如何对齐（例如价格快照 vs 当前价）？
- SKU/客户/渠道参数不存在或不合法时，系统返回的错误是否可用于前端直接提示用户？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在下单提交时执行服务端二次可售校验，并以单一权威口径判断是否可下单（避免前后端分散判断）。
- **FR-002**: 系统 MUST 在下单提交时校验库存是否充足，库存口径必须使用“可用库存 = 可用数量 - 已锁数量”的一致定义。
- **FR-003**: 系统 MUST 在订单创建成功时锁定对应 SKU 库存；若订单创建失败或校验失败，库存锁定 MUST 不发生。
- **FR-003A**: 系统 MUST 支持小程序购物车（混合模式）：本地购物车离线可用；登录后支持与服务端购物车同步并合并。
- **FR-004**: 系统 MUST 支持客户侧创建订单并查询订单列表/详情，且仅能访问自身订单数据。
- **FR-005**: 系统 MUST 支持后台为指定客户创建订单（代客下单），并与客户订单保持一致的可售/库存口径。
- **FR-006**: 系统 MUST 支持后台查询订单列表与订单详情，至少包含订单状态、金额汇总、明细项与创建时间等关键信息。
- **FR-007**: 系统 MUST 支持后台取消订单；取消成功后 MUST 释放对应库存锁定，并将订单状态更新为已取消。
- **FR-008**: 系统 MUST 记录订单关键事件（例如创建、取消）及操作者信息，并支持后台查看操作日志以进行追溯。
- **FR-009**: 订单 MUST 至少支持以下状态：`draft`（仅后台可见/可编辑）、`pending_payment`（已创建待支付）、`paid`（可选：模拟）、`cancelled`。
- **FR-010**: 系统 MUST 在订单创建时保存关键数据快照（例如价格/金额/可售判断结果的关键字段），以确保后续查询与追溯的一致性。
- **FR-011**: 系统 MUST 支持“创建订单”的幂等提交：同一幂等键在其有效期内重复提交时，返回同一订单创建结果且不得重复锁定库存（适用于小程序与后台代客下单）。
- **FR-012**: 系统 MUST 仅允许后台（运营/客服）取消订单，且仅 `pending_payment` 状态允许取消；`paid` 在 MVP 中不得取消；`draft` 可按“作废/删除草稿”处理但不视为取消订单。
- **FR-013**: 系统 MUST 以“提交时服务端计算的当前价”生成订单单价与金额汇总，并保存价格/金额快照；当展示价与提交价不一致时，MVP 不做二次确认门槛。
- **FR-014**: 当一次下单包含多个 SKU 时，系统 MUST 采用整单原子语义：任一明细项不可售或库存不足则整单创建失败，且不得创建订单记录或锁定任何库存。
- **FR-015**: 系统 MUST 生成并对外展示“人可读订单号”，且该订单号在同一租户内必须唯一，便于后台检索与客服沟通。
- **FR-016**: 购物车 MUST 不锁库存（不写 locked_qty）；库存锁定只发生在订单创建成功的事务内。
- **FR-017**: 系统 MUST 提供客户收货地址簿（多地址）能力：创建/更新/删除/设置默认；并确保客户仅能管理自己的地址。
- **FR-018**: 系统 MUST 在创建订单时保存收货地址**快照**到订单记录（不可变历史），并在订单详情接口返回该快照；若使用地址簿下单，订单 SHOULD 记录 `shipping_address_id` 以便追溯来源地址。
- **FR-019**: 系统 MUST 提供小程序地址簿接口（受保护）：`GET /mini-app/me/addresses`、`POST /mini-app/me/addresses`、`PATCH /mini-app/me/addresses/{id}`、`DELETE /mini-app/me/addresses/{id}`、`POST /mini-app/me/addresses/{id}/default`。
- **FR-020**: 系统 MUST 提供后台按客户管理地址簿接口（受 RBAC + tenant 保护）：`GET/POST/PATCH/DELETE /admin/customers/{customerId}/addresses` 与 `POST /admin/customers/{customerId}/addresses/{id}/default`。
- **FR-021**: 对于需要收货的订单，创建订单请求 MUST 指定收货地址（地址簿 `shippingAddressId` 或直接提交 `shippingAddress`），否则返回可解释错误。

### Key Entities *(include if feature involves data)*

- **Cart（购物车）**: 面向 customer 的 SKU 列表与数量集合；支持本地保存与服务端同步合并；不承担库存锁定职责。
- **Order（订单）**: 表示一次下单交易；包含客户、渠道、状态、金额汇总、创建时间、关键快照等信息。
- **Order Item（订单明细）**: 表示订单内每个 SKU 的购买项；包含 SKU、数量、单价与行金额等信息。
- **Order Event（订单事件/审计）**: 表示订单生命周期内的关键操作记录；包含事件类型、操作者、发生时间与关键字段。
- **Customer Address（收货地址/地址簿）**: 表示客户可维护的收货地址记录；支持多条与默认地址；订单创建时会复制为快照以形成历史不可变记录。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在可售且库存充足的前提下，客户/运营发起下单后可在 2 秒内获得“订单创建成功”响应（不含支付）。
- **SC-002**: 对于不可售或库存不足的下单请求，系统 100% 返回明确失败原因，且不会产生订单记录或库存锁定副作用。
- **SC-003**: 库存锁定准确性：对同一 SKU 的并发下单不出现超卖；订单取消后库存锁定在 5 秒内释放且可再次下单成功（在库存充足时）。
- **SC-004**: 后台可在订单创建后 10 秒内在订单列表中检索到该订单，并在详情页看到与创建时一致的状态/金额/明细信息。
