## Scope / Assumptions / Dependencies

- **范围（MVP）**：仅覆盖“SKU 维度库存闭环（可写 + 可读快照）”与“上架前置校验的库存部分”；不包含仓库拓扑、调拨、盘点、批次/效期、预测补货、与外部 WMS/OMS 的实时同步。
- **默认维度**：MVP 仅以 `default` 仓作为库存归属维度；若未来引入多仓/渠道库存，需在此规格基础上扩展口径与 UI。
- **字段语义**：`locked_qty`、`in_transit_qty` 在 MVP 允许为 0，但字段与语义必须稳定，为后续订单锁定/调拨在途扩展预留空间。
- **依赖**：依赖商品域已存在 SKU 主数据；上架/发布的最终可售校验将与“价格是否存在”的规则一起落地（本规格仅定义库存侧最小要求）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 运营可为 SKU 写入可用库存 (Priority: P1)

商品/仓储运营可以为某个 SKU 写入（或调整）可用库存，使该 SKU 进入“可售”的可控状态；并能在后台看到写入后的库存快照（可用/锁定/在途）。

**Why this priority**: 没有“可写库存”，库存视图与上架判断都无法与真实业务对齐，产品上架链路无法形成闭环。

**Independent Test**: 仅实现“对单个 SKU 写入 default 仓可用库存 → 读取库存快照验证”即可独立验收。

**Acceptance Scenarios**:

1. **Given** 存在一个 SKU 且当前无库存记录或库存为 0，**When** 运营执行一次“增量调整” `delta=+10`，**Then** 系统应返回成功且库存快照中该 SKU 的 `available_qty` 为 10。
2. **Given** 已存在库存记录且 `available_qty=10`，**When** 运营执行一次“增量调整” `delta=-7`，**Then** 系统应返回成功且库存快照中 `available_qty` 变为 3。
3. **Given** 已存在库存记录且 `available_qty=3`，**When** 运营执行一次“增量调整” `delta=-5` 导致结果为负数，**Then** 系统应拒绝并返回可解释的错误信息（禁止可用库存为负）。

---

### User Story 2 - web-admin 提供 SKU 库存维护入口 (Priority: P2)

运营在 web-admin 的 SKU 详情页可以直接看到库存快照，并通过输入框提交 `delta` 增量调整 default 仓可用库存（最终影响 `available_qty`），避免必须依赖数据库或脚本才能让 SKU “可售”。

**Why this priority**: “上架链路”必须可由非研发角色操作与验证；否则库存能力只能停留在后端接口阶段。

**Independent Test**: 仅实现“SKU 详情页展示库存 + 更新 available_qty 按钮”即可独立验收，不依赖仓库管理、调拨、盘点等复杂模块。

**Acceptance Scenarios**:

1. **Given** 运营打开某个 SKU 详情页，**When** 页面加载完成，**Then** 页面应展示该 SKU 的库存快照（至少包含可用/锁定/在途字段；未实现字段可显示 0 或“暂无”）。
2. **Given** 运营在库存卡片输入一次增量调整 `delta=+10` 并保存，**When** 保存成功，**Then** 页面应显示最新快照且刷新后仍一致。
3. **Given** 接口返回权限不足或校验失败，**When** 保存库存，**Then** 页面应展示可理解的错误提示且不应造成页面崩溃。

---

### User Story 3 - 上架/发布的库存前置校验 (Priority: P3)

当运营尝试把 SPU 发布/上架**或**把商品同步到渠道上架时，系统应执行最小化校验：至少存在 1 个“可售”SKU（符合可售库存口径），否则不允许继续上架（或强制下架/保持草稿）。

**Why this priority**: 当前“无库存仍可上架”的行为会导致前台/小程序出现无法履约的商品，增加售后与渠道处罚风险。

**Independent Test**: 不依赖全量库存模块，仅依赖“SKU 可写库存 + SKU 库存快照 + 上架流程的校验点”即可独立验收。

**Acceptance Scenarios**:

1. **Given** 某 SPU 已有价格但其所有 SKU 的可售库存均为 0，**When** 运营执行 **SPU 发布** 操作，**Then** 系统应阻止并返回“缺少可售库存”的可解释原因。
2. **Given** 某 SPU 已有价格但其所有 SKU 的可售库存均为 0，**When** 运营执行 **渠道上架/同步发布** 操作，**Then** 系统应阻止并返回“缺少可售库存”的可解释原因。
3. **Given** 某 SPU 至少有 1 个 SKU 的可售库存 > 0，**When** 运营执行发布/上架或渠道上架操作，**Then** 系统允许继续，并在前台/小程序侧能购买到该 SKU（以现有销售流程为准）。
4. **Given** 库存校验未通过，**When** 系统阻止发布/上架，**Then** 商品的状态不应被系统自动更改（仅返回失败原因供运营修正后重试）。

### Edge Cases

- 并发写入：同一 SKU 被多次快速更新库存时，最终快照应可预测（最后写入生效或按业务规则合并），且不应出现“读到旧值/脏写”导致的不可解释结果。
- 并发调整：同一 SKU 被并发执行多次增量调整时，应避免出现“最终可用库存为负/结果不可解释”的情况（至少保证最终值不为负，并返回可定位的冲突/失败原因）。
- 缺少 SKU / 租户隔离：写入或读取不存在的 SKU，或跨租户 SKU，应返回明确错误且不泄漏数据。
- 只实现 default 仓：当 SKU 存在多仓库存但 MVP 未支持时，前台与上架校验应明确只以 default 仓口径判断（或在 UI 上提示）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以 SKU 为粒度提供库存快照读取能力，至少覆盖可用库存（available）、锁定（locked）、在途（in_transit）三类数量字段（即使后两者在 MVP 仅返回 0 也需字段语义一致）。
- **FR-002**: 系统 MUST 提供“写入/调整 SKU 库存”的后台能力，用于更新 default 仓的可用库存数量，并保证结果可被后续读取验证。
- **FR-002A**: 系统 MUST 将本阶段库存写入定义为“增量调整（delta）”语义：输入变更量 `delta`，系统基于当前可用库存计算新值；并保证调整过程不会产生负数可用库存。
- **FR-002B**: 系统 MUST 将 `delta` 限定为整数单位（按“件”计数）；MVP 不支持小数库存。
- **FR-003**: 系统 MUST 校验库存写入请求：数量不可为负；目标 SKU 必须存在且属于当前租户；无权限的操作者不得写入。
- **FR-004**: 系统 MUST 记录库存写入的必要审计信息（操作者、时间、SKU、变更前/后数量或变更量），以便问题追溯。
- **FR-005**: web-admin MUST 在 SKU 详情页提供库存展示与写入入口，并对错误进行友好提示（不影响其它模块使用）。
- **FR-006**: 系统 MUST 在“SPU 发布/上架”与“渠道上架/同步发布”的关键动作中增加库存前置校验：至少存在 1 个 SKU 满足“可售库存口径”，否则阻止继续动作并返回可解释原因。
- **FR-006A**: 系统 MUST 固化本阶段“可售库存（salable）”口径为：`available_qty > 0`（仅评估 default 仓的可用库存，MVP 不引入 safety_stock 计算）。
- **FR-006B**: 系统 MUST 在库存校验失败时采取“仅阻止”策略：返回可解释原因并保持商品当前状态不变（不执行自动下架/自动状态切换）。
- **FR-007**: 系统 MUST 保持与 `docs/plan/inventory/stock.md` 的库存状态语义一致：可用/锁定/在途字段含义清晰、可复用，并为后续锁定/释放、调拨、盘点扩展预留空间。

### Key Entities *(include if feature involves data)*

- **SKU 库存 (SKU Inventory)**: 表示某 SKU 在某个仓库维度下的库存状态快照（可用/锁定/在途等），用于上架判断与履约计算。
- **仓库 (Warehouse)**: 表示库存归属的物理或逻辑仓。MVP 以 `default` 仓作为最小闭环的默认维度。
- **库存审计记录 (Inventory Audit Log)**: 记录库存写入/调整操作的可追溯信息，用于排查、对账与权限审计。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运营人员无需数据库操作即可在 ≤ 2 分钟内完成：打开某 SKU 详情页 → 将 default 仓 `available_qty` 写为 10 → 刷新后仍能看到一致的库存快照。
- **SC-002**: 当 SPU 下所有 SKU 可售库存为 0 时，发布/上架动作能被稳定阻止，并返回可理解的原因（不依赖日志排查）。
- **SC-003**: 当 SPU 至少存在 1 个 SKU 可售库存 > 0 时，发布/上架动作可继续，且前台/小程序侧能看到“可售商品”而非不可履约商品（以现有前台展示/购买逻辑为准）。
