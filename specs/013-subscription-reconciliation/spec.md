# Feature Specification: 订阅对账与续费治理

**Feature Branch**: `013-subscription-reconciliation`  
**Created**: 2026-03-31  
**Status**: Draft  
**Input**: User description: "订阅对账与续费治理"

## Clarifications

### Session 2026-03-31

- Q: 对账“应收金额”口径怎么定义？ → A: 按用户应付净额（账单金额 + 税费 - 优惠）
- Q: 差异处置任务的默认 SLA 多久？ → A: 按差异等级分层（高 24h / 中 48h / 低 72h）
- Q: 续费失败后的自动重试策略默认采用哪种？ → A: 递增间隔 4 次（1h、24h、72h、7d）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 每日订阅对账闭环 (Priority: P1)

作为财务/运营，我需要每天看到“应收金额、实收金额、差异金额、差异原因”的对账结果，并可一键生成待处理工单，避免订阅收入漏收或重复记账。

**Why this priority**: 对账准确是现金流和合规底线，若无此能力，后续续费优化没有可信数据基础。

**Independent Test**: 准备一批包含正常、漏扣、重复扣费、金额不一致的数据样本，执行一次日对账，验证系统能输出差异清单并生成工单。

**Acceptance Scenarios**:

1. **Given** 存在当日订阅账单与支付流水，**When** 运营发起日对账，**Then** 系统输出对账汇总（应收/实收/差异）及可追溯差异明细。
2. **Given** 差异明细已生成，**When** 运营选择“创建处置任务”，**Then** 系统为每条差异生成唯一任务并标记任务状态为待处理。

---

### User Story 2 - 自动续费失败治理 (Priority: P2)

作为订阅运营，我需要对自动续费失败用户执行分批重试和提醒流程，并跟踪恢复情况，降低非主动流失。

**Why this priority**: 在有了对账基线后，续费恢复是直接提升收入的高回报动作。

**Independent Test**: 构造一批续费失败用户，执行“重试策略 + 通知策略”，验证部分用户恢复成功、其余进入升级处置。

**Acceptance Scenarios**:

1. **Given** 用户续费失败且可重试，**When** 系统到达重试窗口，**Then** 系统按规则发起重试并记录结果。
2. **Given** 用户连续重试失败，**When** 达到策略阈值，**Then** 系统触发升级处置（例如转人工跟进）并保留完整过程记录。

---

### User Story 3 - 差异责任归因与看板 (Priority: P3)

作为经营管理者，我需要按渠道、套餐、失败原因查看对账与续费治理效果，便于快速定位高风险区域并持续优化策略。

**Why this priority**: 决策分析价值高，但不阻塞 P1/P2 的核心闭环。

**Independent Test**: 执行一轮对账与续费治理后，验证看板能输出周期指标和归因分布，且可按维度筛选。

**Acceptance Scenarios**:

1. **Given** 已存在一段周期内的对账与续费处理数据，**When** 管理者查看分析看板，**Then** 可看到差异率、恢复率、处理时长与原因分布。

---

### Edge Cases

- 同一订阅在短时间内出现重复支付记录时，系统必须只认定一个有效收款并标识其余为异常候选。
- 支付状态延迟回传导致“先失败后成功”时，系统必须在下一次对账中自动纠正差异状态，避免重复创建任务。
- 账单金额发生合法变更（例如套餐升级）但支付按旧金额完成时，系统必须将其归为“金额不一致”并提示人工判定。
- 对账任务重复触发时，系统必须保证幂等，避免产生重复差异任务。
- 租户在账期中途停用某支付渠道时，系统仍需产出完整对账结论并明确“数据不完整”标记。

### Assumptions

- 现有系统已具备“订阅账单数据、支付流水数据、运营任务中心、通知触达”基础能力。
- 本特性默认按“日对账”推进，后续可扩展至周/月账期，但不影响当前范围定义。
- 本特性默认适用于多租户场景，所有结果均按租户维度隔离展示与导出。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须支持按租户与账期生成订阅对账结果，输出应收金额、实收金额、差异金额和差异条数。
- **FR-001a**: 对账中的“应收金额”必须统一采用用户应付净额口径（账单金额 + 税费 - 优惠），并在全量报表与看板保持一致。
- **FR-002**: 系统必须为每条差异记录提供标准化差异类型（漏收、重复收款、金额不一致、状态不一致、数据缺失）。
- **FR-003**: 系统必须允许运营将差异记录转为处置任务，并记录责任人、优先级、处理状态与处理结论。
- **FR-003a**: 差异处置任务默认 SLA 必须按风险等级分层：高风险 24 小时、中风险 48 小时、低风险 72 小时。
- **FR-004**: 系统必须支持续费失败的分阶段治理流程，包括自动重试、通知触达、升级处置三类动作。
- **FR-004a**: 自动重试默认策略必须为递增 4 次重试窗口（1 小时、24 小时、72 小时、7 天），并允许记录每次窗口执行结果。
- **FR-005**: 系统必须记录每次续费治理动作的执行时间、执行结果与失败原因，供审计追溯。
- **FR-006**: 系统必须阻止同一订阅账期下重复创建“未关闭”的差异处置任务。
- **FR-007**: 系统必须支持按渠道、套餐、国家/地区、失败原因等维度查询对账与治理结果。
- **FR-008**: 系统必须提供面向运营的治理看板，展示差异率、恢复率、平均处理时长、待处理积压量。
- **FR-009**: 系统必须支持手工纠偏操作，并将纠偏前后关键字段变化纳入审计日志。
- **FR-010**: 系统必须在账期结束后支持导出对账与治理结果，用于财务归档与外部审计。

### Key Entities *(include if feature involves data)*

- **订阅账单周期 (Billing Cycle)**: 描述某租户在特定时间窗口内应收的订阅账单集合，关键属性包括账期、应收金额、账单数量、状态。
- **对账结果 (Reconciliation Result)**: 记录账单与支付匹配后的输出，关键属性包括实收金额、差异金额、差异率、生成时间。
- **差异记录 (Reconciliation Delta)**: 表示单条异常项，关键属性包括差异类型、关联订阅、关联账单、关联支付、风险等级、当前状态。
- **差异处置任务 (Delta Task)**: 表示运营跟进单，关键属性包括负责人、优先级、处理动作、处理时长、结论。
- **续费治理策略 (Renewal Governance Policy)**: 定义重试节奏、触达规则、升级阈值的策略实体。
- **治理执行记录 (Governance Execution Log)**: 记录每次重试/通知/升级动作，关键属性包括动作类型、执行结果、失败原因、执行时间。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运营在每天账期结束后 30 分钟内可获得完整对账结果，且可直接定位到全部差异明细。
- **SC-002**: 上线后 30 天内，订阅漏收与重复收款导致的人工投诉工单数量下降 40%。
- **SC-003**: 续费失败用户中，至少 25% 可在 72 小时内通过自动治理恢复为有效订阅。
- **SC-004**: 差异处置任务中，90% 可在 2 个工作日内闭环（完成或明确升级）。
- **SC-005**: 抽样审计中，对账与治理链路关键字段的可追溯完整率达到 100%。
