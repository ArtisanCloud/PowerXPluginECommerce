## Clarifications

### Session 2025-12-11

- Q: 批量导入过程中若部分行校验失败，是否允许其它行先入库？ → A: 允许成功行立即写入，失败行跳过并在任务报告中给出错误明细，供运营修复后重试。
- Q: 订阅计划变更时是否影响存量订阅？ → A: 发布变更时可选择仅影响新订阅或同时影响存量订阅，默认只作用于新订阅，特殊情况下可扩展到存量并触发必要提醒。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 全流程创建并发布 SPU (Priority: P1)

商品运营进入 SPU 列表后，可以通过创建向导选择类目/模板、录入多语言内容、配置订阅计划（如适用）并在草稿状态下多次保存，最终提交审核并发布。

**Why this priority**: 新品上线是商品中心最核心的价值流，若无法创建并发布，其他功能没有意义。

**Independent Test**: 通过一次完整的「创建→编辑→提交审核→发布」流程验证数据保存、状态转换与发布推送是否按预期工作。

**Acceptance Scenarios**:

1. **Given** 商品运营在列表页点击“创建 SPU”，**When** 依步骤完成类目、基础信息、媒体与渠道配置并提交，**Then** 系统创建新 SPU 并进入“审核中”状态，同时生成待审任务。
2. **Given** 运营在草稿状态关闭页面，**When** 再次打开同一 SPU，**Then** 所有已填写字段（含多语言、订阅计划）应完整保留且可继续编辑。
3. **Given** 审批通过的 SPU，**When** 发布成功，**Then** 列表状态更新为“已发布”且指定渠道收到上架任务回执。

---

### User Story 2 - 审批与版本控制 (Priority: P2)

品控/法务等审批角色可查看提交的版本差异、添加意见、按既定顺序审批；商品运营可查看历史版本并在需要时回滚。

**Why this priority**: 审批合规直接影响上线风险与合规性，版本追踪支撑审计与回滚需求。

**Independent Test**: 通过提交变更后触发多级审批、查看差异、驳回/回滚任一版本即可验证流程独立性。

**Acceptance Scenarios**:

1. **Given** SPU 处于“审核中”，**When** 品控完成审批并添加意见，**Then** 审批链应记录该意见、时间与人员并自动流转至下一审批节点。
2. **Given** 已发布 SPU 有多个历史版本，**When** 运营选择任一旧版本并点击“回滚”，**Then** 系统生成新的草稿版本并保留完整的审计记录。

---

### User Story 3 - 渠道发布与批量运营 (Priority: P3)

渠道运营或商品运营需要批量导入/导出商品、配置不同渠道的可售性、定时上下架计划，并在任务中心查看同步结果。

**Why this priority**: 批量与渠道能力决定运营规模化效率，直接影响 GMV 与渠道一致性。

**Independent Test**: 通过上传导入模板、执行批量发布/下架、查看渠道反馈的流程即可独立验证，无需依赖其他故事实现。

**Acceptance Scenarios**:

1. **Given** 运营在详情页配置渠道可见性，**When** 针对不同渠道设置上架时间、内容差异并发布，**Then** 各渠道应按计划收到对应内容并反馈状态。
2. **Given** 运营批量上传导入模板，**When** 校验通过且任务完成，**Then** 系统提供成功/失败报告并允许对失败条目逐条修复后重试。

---

### Edge Cases

- 当导入文件内存在重复的 SPU 编码或 SKU 关联时，系统应拒绝整行并在报告中标记重复来源。
- 当审批链任一节点超过 SLA（如 2 个工作日）未响应时，应向责任人和管理员发送提醒并允许重新指派。
- 当渠道审核返回失败原因时，列表与详情需展示渠道回执并允许仅针对该渠道重新推送。
- 当订阅计划变更的生效时间晚于当前发布版本但早于下一次发布窗口时，需提示运营选择立即生效（触发紧急审批）或按计划延后。
- 当多语言内容缺失关键字段（如默认语言标题）时，系统必须阻止提交审核并提示必填语言组合。

### 下架策略（Offboarding）

- **触发方式**：运营可在详情页选择“下架”动作，按渠道勾选并可设置 `withdrawAt`（立即或定时）。每次动作都需填写理由，写入审计。
- **状态流转**：渠道级别 `availability` 或 `audit_state` 置为 `offboarded`，当所有渠道都标记为下架后，SPU 总状态改为 `offboarded`。若只部分渠道下架，SPU 保持 `published` 并在渠道摘要里展示混合状态。
- **任务与通知**：后端调用 `POST /api/v1/admin/product/spus/{id}/withdraw` 生成异步任务，推送给渠道任务中心；任务回执写入审计时间轴，并在“渠道发布”看板显示。
- **权限与审批**：下架不再走版本审批，但要求具备 `product.spu.publish` 或更高权限；如定时下架晚于 24 小时，可选触发额外确认（未来扩展）。
- **回滚/复上**：若下架后需重新上架，运营需创建新版本或复用既有版本重新走“提交→审批→发布”流程，确保流程一致。

### 删除策略（Soft vs Hard Delete）

- **软删除**：利用表中的 `deleted_at` 字段。仅允许处于 `draft` 或 `offboarded` 状态的 SPU 执行软删除；执行后保留版本、审批、渠道历史，但在列表与检索中默认隐藏。删除动作必须写入审计日志，说明原因与操作者。已发布或 `reviewing` 状态需先下架/驳回方可删除。
- **硬删除**：仅限平台管理员执行，且需要满足：SPU 已软删除 ≥30 天、无绑定任务/渠道运行中、无 SKU/订单引用。硬删除会级联清理 `product_spu_versions`、`product_spu_channels`、`product_spu_subscription_plans`、`product_spu_audit_logs` 等数据，并产出审计记录。默认不在 UI 暴露，需通过后台运维脚本触发。
- **限制**：当 SPU 存在尚未完成的审批/任务、或被其他模块引用（如套餐、营销活动）时，禁止软/硬删除，并给出提示。对于合规要求，保留软删除记录至审计系统，不允许直接绕过。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供可配置步骤的创建向导，支持基于类目/模板自动加载必填字段与默认属性。
- **FR-002**: 系统必须允许在 SPU 中维护多语言文本字段，可在默认语言与额外语言间批量复制与校验必填状态。
- **FR-003**: 系统必须支持 SPU 状态在草稿、审核中、已发布、下架之间转换，并记录转换触发人及时间。
- **FR-004**: 系统必须在每次保存或提交前生成版本快照，展示字段差异并允许回滚至任一历史版本。
- **FR-005**: 系统必须支持可配置多级审批流（商品运营→品控→法务），每级可添加意见、附件并遵循 SLA 通知。
- **FR-006**: 系统必须允许在 SPU 内配置渠道可见性（渠道列表、上架/下架时间、内容差异、可售地区）并触发同步任务。
- **FR-007**: 系统必须提供批量导入导出能力，导入时对类目、SKU 唯一性与必填字段进行校验，允许校验通过的行立即入库，失败行跳过并在任务结果报告中给出可追溯错误明细，便于逐条修复后重试。
- **FR-008**: 系统必须允许在 SPU 中新增、编辑、禁用订阅计划，支持计费周期、价格、试用期、自动续费、取消策略等参数，并在发布变更时提供“仅新订阅”与“新+存量订阅”两种作用范围选项（默认为仅新订阅），若选择影响存量需记录额外审批与提醒。
- **FR-009**: 系统必须在 SPU 中关联 SKU，可批量创建/复制 SKU 并继承属性、同步库存与定价模块。
- **FR-009A**: 系统必须允许草稿 SPU 从所属品类的销售规格模板显式同步规格维度与取值，并允许运营在 SPU 内裁剪后保存；同步动作不得静默覆盖已保存规格。
- **FR-010**: 系统必须记录包括字段变更、审批意见、导入导出、渠道推送在内的完整审计日志，支持按时间和操作人查询。

### SPU 规格同步业务说明

SPU 负责决定“这个商品实际卖哪些规格”。品类只提供标准模板，SPU 同步后可以裁剪。

操作例子：

```text
品类：毛绒玩具
  标准销售规格：
    尺寸：10cm、20cm、30cm
    体型：普通体、海星体、骨架体
    工艺：印花、绣花

SPU：努努娃娃
  运营点击“从品类同步”
  系统带入全部标准销售规格
  运营删除不卖的：
    尺寸：30cm
    体型：普通体
    工艺：印花、绣花

SPU 最终保存：
  尺寸：10cm、20cm
  体型：海星体、骨架体
```

保存后的 SPU 规格才会进入 SKU 生成器。品类模板后续变更不会自动改动这个 SPU，必须由运营再次显式同步并保存。

### Key Entities *(include if feature involves data)*

- **SPU**: 商品的跨渠道主实体，包含多语言基本信息、品类、品牌、商品类型、标签以及关联的媒体和渠道配置。
- **SPU Version**: 对 SPU 任一编辑提交时生成的变体，储存差异字段、状态、提交人、审批记录，可被预览与回滚。
- **Channel Visibility**: 描述每个渠道的可售状态、上架/下架时间、内容 overrides 以及渠道审核回执。
- **Subscription Plan**: 针对订阅型商品的计划配置，包含计费周期、价格、试用期、自动续费策略、取消与代扣规则。
- **Import/Export Task**: 记录批量导入导出的任务、校验结果、成功/失败明细和可下载的报告。
- **Approval Record**: 保存每个审批节点的状态、意见、附件、SLA 计时和责任人信息。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 80% 新建 SPU 可在 2 天内（含审批）完成从草稿到已发布的全流程。
- **SC-002**: 批量导入任务的成功率 ≥ 99%，失败条目均生成可下载的错误报告。
- **SC-003**: 渠道同步成功率 ≥ 98%，若渠道拒绝则在 1 小时内向运营展示回执信息。
- **SC-004**: 审批 SLA 达成率 ≥ 95%，超时节点全部触发提醒或自动重新分配。
- **SC-005**: 所有 SPU 变更 100% 被审计日志捕获，可按 SPU 和时间区间检索。

## Assumptions

1. 审批流与公司统一审批中心对接，允许在本系统中查看与操作，无需重复建模。
2. 渠道推送任务由既有渠道任务中心执行，本功能负责生成任务 payload 并展示回执。
3. 多语言列表与可用渠道、类目等基础数据由主数据服务提供，且在页面加载时可实时获取。
4. 批量导入使用标准 Excel/CSV 模板，由商品运营在桌面端上传。
