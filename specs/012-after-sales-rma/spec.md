# Feature Specification: 售后 RMA 与退货门户

**Feature Branch**: `012-after-sales-rma`  
**Created**: 2026-03-31  
**Status**: Draft  
**Input**: User description: "构建售后RMA业务模块：以reverse-logistics为主模块，覆盖退款/退货/换货申请、审核与状态流转；补充customer returns portal最小入口与进度查询；并与订单、支付、履约状态做最小联动。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 客户提交售后申请并跟踪进度 (Priority: P1)

客户在订单已支付且满足售后条件时，可以发起退款、退货退款或换货申请，并在用户侧持续查看当前处理状态与下一步动作。

**Why this priority**: 这是售后模块最核心入口，直接决定用户是否能完成售后闭环，影响投诉率与复购信任。

**Independent Test**: 仅实现该故事时，用户应可完成“提交申请 -> 查询进度 -> 查看处理结果”全链路，不依赖后台高级能力。

**Acceptance Scenarios**:

1. **Given** 客户存在可申请售后的订单明细，**When** 客户提交售后类型与原因，**Then** 系统创建唯一售后单并返回申请编号与初始状态。
2. **Given** 客户已提交售后申请，**When** 客户进入售后入口查询，**Then** 系统返回按时间倒序的申请列表与每单最新状态。
3. **Given** 售后单状态已变化，**When** 客户查看售后详情，**Then** 系统展示当前状态、状态变更时间与处理说明。

---

### User Story 2 - 运营审核与标准化流转 (Priority: P1)

运营人员在后台对售后申请进行受理、审核、驳回、完成等标准操作，系统执行受控状态流转并保留操作轨迹。

**Why this priority**: 没有后台审核与状态流转，前台申请无法落地处理，业务无法形成可执行流程。

**Independent Test**: 仅实现该故事时，运营应可对新建售后单完成至少一条完整路径（通过或拒绝），并可回溯每次操作。

**Acceptance Scenarios**:

1. **Given** 存在“待受理”售后单，**When** 运营执行受理并进入审核，**Then** 状态按规则推进且记录操作人、时间、备注。
2. **Given** 运营审核不通过，**When** 提交驳回原因，**Then** 系统将售后单更新为拒绝状态并对客户侧可见。
3. **Given** 售后单已满足完成条件，**When** 运营执行完结，**Then** 系统将售后单置为完成并冻结后续非法状态变更。

---

### User Story 3 - 订单/支付/履约最小联动 (Priority: P2)

售后单在关键节点与订单、支付、履约信息形成一致性联动，避免多系统状态冲突与重复处理。

**Why this priority**: 联动可降低对账和客服冲突成本，但在 MVP 阶段优先级低于“申请+审核”主流程。

**Independent Test**: 仅实现该故事时，创建并推进售后单后，应可观察到订单侧售后标记与退款/退货相关联动结果。

**Acceptance Scenarios**:

1. **Given** 退款类售后审核通过，**When** 进入退款处理中，**Then** 系统在订单侧标记对应售后进度并防止重复退款申请。
2. **Given** 退货类售后进入待收货，**When** 履约侧确认收货结果，**Then** 售后单同步推进至下一合法状态。
3. **Given** 订单已取消或不满足售后窗口，**When** 发起售后申请，**Then** 系统拒绝申请并返回明确原因。

### Clarifications

- **CL-001（时间窗口）**: 采用分层窗口规则：
  - 仅退款：付款后 24 小时且订单未发货。
  - 退货退款：签收后 7 天内。
  - 换货：签收后 15 天内。
- **CL-002（重复申请）**: 同一订单明细在“进行中”状态禁止重复申请；进入终态后允许再次发起，但必须创建新售后单并填写新原因。
- **CL-003（换货边界）**: 首版开放换货申请，但仅支持申请、审核、状态回填与处理备注，不包含自动补发与库存自动占用。

### Edge Cases

- 同一订单明细在已有进行中售后单时，重复提交申请应被拒绝并返回已存在申请编号。
- 客户提交的申请类型与订单履约状态不匹配时（例如未发货却申请“退货退款”），系统应给出可理解的校验失败原因。
- 审核过程中发生并发操作（两名运营同时处理同一售后单）时，仅允许一个操作成功，另一方收到状态已变更提示。
- 售后单进入终态（拒绝/完成/关闭）后，任何继续流转请求都应被阻止并记录尝试行为。
- 客户查询不存在或不属于本人的售后单时，不返回敏感信息，只返回“无权限或不存在”。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持客户针对订单明细发起三类售后申请：仅退款、退货退款、换货。
- **FR-002**: 系统 MUST 在创建申请时校验订单状态、支付状态、售后时间窗口与明细归属，未通过时拒绝创建。
- **FR-002A**: 系统 MUST 按售后类型执行分层时间窗口：仅退款（付款后 24 小时且未发货）、退货退款（签收后 7 天内）、换货（签收后 15 天内）。
- **FR-003**: 系统 MUST 为每个售后申请生成全局唯一申请编号，并记录申请来源、申请类型、原因、凭证与备注信息。
- **FR-004**: 系统 MUST 提供客户侧售后列表与详情查询，包含当前状态、状态时间线与处理说明。
- **FR-005**: 系统 MUST 提供后台售后工作台能力，支持受理、审核通过、审核拒绝、完结与关闭等动作。
- **FR-006**: 系统 MUST 定义并执行售后状态机，任何不合法的状态跳转必须被拒绝。
- **FR-007**: 系统 MUST 在每次状态变化时记录审计轨迹，至少包含操作者、动作、时间、前后状态与备注。
- **FR-008**: 系统 MUST 防止同一订单明细在同一时段内出现重复进行中的售后申请。
- **FR-008A**: 系统 MUST 允许同一订单明细在历史售后单已终态后再次申请，并将其作为独立新单处理。
- **FR-009**: 系统 MUST 在退款类售后进入关键节点时，向订单侧同步售后标记与处理结果，确保订单展示一致。
- **FR-010**: 系统 MUST 在退货类售后中支持录入或关联逆向物流信息，并将收货结果反馈到售后状态推进。
- **FR-011**: 系统 MUST 为后台提供按状态、申请类型、时间范围、订单号、客户关键词的检索能力。
- **FR-012**: 系统 MUST 支持客户与运营分别查看其有权限的数据范围，禁止跨租户、跨主体访问。
- **FR-013**: 系统 MUST 在售后单进入终态后禁止继续修改核心业务字段，仅允许追加备注或审计说明。
- **FR-014**: 系统 MUST 对外返回统一的失败原因分类（校验失败、状态冲突、权限不足、数据不存在），便于前台展示与运营排查。
- **FR-015**: 系统 MUST 提供售后统计基础视图（待处理、处理中、已完成、已拒绝）以支撑运营日常排班。
- **FR-016**: 系统 MUST 在首版将换货处理边界限定为“申请 + 审核 + 状态回填 + 备注记录”，不触发自动补发与库存自动占用。

### Key Entities *(include if feature involves data)*

- **AfterSaleCase（售后单）**: 表示一次售后申请，关键属性包括申请编号、订单明细引用、申请类型、当前状态、原因、金额/数量范围、申请人与时间。
- **AfterSaleTimeline（售后轨迹）**: 表示售后状态变化与处理动作的时间线记录，关键属性包括动作、前后状态、操作者、备注、发生时间。
- **AfterSaleEvidence（售后凭证）**: 表示用户或运营上传/补充的证据信息，关键属性包括凭证类型、说明、关联售后单、提交人、提交时间。
- **AfterSaleDecision（审核决策）**: 表示运营审核结论，关键属性包括结论类型、原因分类、处理建议、决策人、决策时间。
- **ReturnLogisticsLink（逆向物流关联）**: 表示退货类售后与逆向物流过程的关联，关键属性包括物流单号、承运方标识、收货确认状态、确认时间。

### Assumptions

- MVP 阶段仅覆盖单租户内业务流程，不包含跨租户协同处理。
- MVP 阶段优先保障“标准审核流”，复杂仲裁/多级审批/自动仲裁不在本期范围。
- 换货流程在本期先以“创建换货申请 + 后台处理结果回填”为边界，不引入复杂库存重分配策略。
- 与支付、履约的联动以“状态同步与防重”为最低目标，不在本期扩展完整财务结算策略。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 90% 以上的客户可在 2 分钟内完成一次售后申请提交（从进入入口到提交成功）。
- **SC-002**: 95% 以上的售后申请在提交后 5 秒内可在客户侧列表中查询到。
- **SC-003**: 售后单状态流转的非法跳转拦截率达到 100%（非法请求全部被拒绝并可审计）。
- **SC-004**: 运营在后台处理“受理 -> 审核 -> 完结/拒绝”标准路径的平均操作时长不超过 3 分钟/单（不含人工等待时长）。
- **SC-005**: 上线后首月，与“售后进度不可见/状态不一致”相关的客服工单占比下降 40% 以上。
